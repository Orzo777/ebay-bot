# eBay price + liquidity monitor → Telegram (німецький ринок)

Персональний інструмент: періодично опитує **офіційний eBay Browse API**
(`X-EBAY-C-MARKETPLACE-ID: EBAY_DE`) по списку категорій й оцінює кожен лот за
**двома незалежними осями**:

1. **ЦІНА** — чи дешевше за **історичну медіану цього товару** (за `epid`), а не
   за медіану поточної текстової видачі.
2. **ЛІКВІДНІСТЬ** — чи товар узагалі швидко купують. Оцінюється **наближено** з
   власного полінгу бота (швидкість зникнення відстежених лістингів як проксі
   продажів). Без Marketplace Insights API точність принципово обмежена → є
   явний стан **UNKNOWN**.

Сповіщення надсилаються, якщо спрацював **ціновий** детектор. Ліквідність його
**не глушить** — лише маркує рівень (`OK / MEDIUM / LOW / UNKNOWN`) і вкладає в
повідомлення пряме посилання на завершені продажі для ручної перевірки.

**Режим розвідки** (`DISCOVERY_MODE=true`, за замовчуванням): бот кілька тижнів
збирає дані по **списку категорій** (17, після перевірки структурної придатності), нічого не шле в Telegram, а
пише кандидатів у `discovery_log.jsonl`. Потім `--discovery-report` рахує score
по кожній категорії, і список звужують до реально прибуткових ніш перед бойовим
режимом. Див. розділ [Режим розвідки](#режим-розвідки-discovery-mode).

**Без скрапінгу HTML.** Тільки REST-виклики Browse API з OAuth2-токеном.

## Дві осі й чому цього замало без ручної перевірки

Ціновий детектор відповідає лише на питання «чи це дешево відносно історії
**цього** товару». Він нічого не каже про те, чи хтось швидко купить товар при
перепродажі. Розрив між цими двома речами — і є ризик «хламу»: ціна статистично
низька, але грошi заморожуються в чомусь, що місяцями лежить без покупця.

Повноцінний сигнал попиту дає лише **Marketplace Insights API** (реальні
sold-лістинги за 90 днів), але його доступ — за окремою заявкою (App Check
ticket на developer.ebay.com), і персональному ключу його зазвичай не дають.
Тому бот будує **власний наближений проксі**, а фінальне рішення лишає за
людиною: у кожному сповіщенні є готове посилання на фільтр **Sold Items** —
хвилина перевірки прибирає весь ризик «дешево, але нікому не треба».

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
# source .venv/bin/activate

pip install -r requirements.txt

# прожити період розвідки (21 день) на mock-даних, тоді звіт по категоріях:

python main.py --discovery-report
```

Без `.env` бот працює на вбудованих mock-даних (`mock_data.py`), а замість
відправки в Telegram друкує повідомлення в консоль з приміткою `[DRY RUN]`.

## Запуск з реальними ключами

```bash
cp .env.example .env      # Windows: copy .env.example .env
# заповніть .env (див. нижче)

python main.py --interval          # цикл, POLL_INTERVAL_SECONDS (за замовч. 1800)
python main.py --once              # один прогін
python main.py --discovery-report  # аналіз зібраних даних розвідки
```

| Прапорець             | Призначення                                                      |
|-----------------------|-----------------------------------------------------------------|
| `--once`              | один прогін і вихід                                              |
| `--interval [SECONDS]`| цикл; без числа = `POLL_INTERVAL_SECONDS` (1800)                 |

## Вісь 1: ЦІНА

### Пошуковий шар: подвійний запит + per-category `min_price`

На живих даних eBay.de виявились дві проблеми, яких не було на mock:

1. `sort=price` (за зростанням) тягне у перші 50 **аксесуарний шум** — поштучні
   LEGO-деталі по €1, захисні стекла для iPhone по €1 — а сам товар (набір за
   €600, телефон за €500) у вибірку не потрапляє.
2. `epid` на eBay.de має **низьке покриття** (часто 0% для запитів типу
   `LEGO 75192`, `iPhone 15`) — багато продавців не привʼязують лот до каталогу.

Рішення:

- **`min_price` на кожну категорію** (`config.py` → `CATEGORIES`) — очікувана
  нижня межа реальної ціни ЦЬОГО товару. Іде у
  `filter=price:[{min_price}..],priceCurrency:EUR` в обох запитах. Значення різні:
  LEGO/iPhone — сотні євро, фільтри пилососів / еспандери / йога — десятки.
- **Подвійний запит на категорію за цикл:**
  - **A** — без `sort` (best_match): репрезентативна популяція для медіани;
  - **B** — `sort=price` (за зростанням): гарантовано ловить найдешевший
    **реальний** лот (шум уже відсічено порогом `min_price`), навіть якщо
    best_match ранжував його поза топ-50.
  - результати обʼєднуються за `item_id`; далі пайплайн не змінюється.

### Гібридний ключ товару (`product_key`)

Замість «сирого» `epid` кожен лот отримує `product_key`:

- є `epid` → ключ `epid:<N>` (точна привʼязка до каталогу, висока впевненість);
- немає `epid` → **грубий підпис із назви**: бренд + модель + місткість/обсяг
  (`128gb`, `24kg`, `65l`…) + бакет стану (`new` / `refurb` за `conditionId`,
  не з тексту). Колір, комплектація, `OVP`, емоційні прикметники — відкидаються.
  Такий ключ позначається **`lower_confidence`**.

Так `iPhone 15 128GB` і `256GB` лишаються різними ключами навіть без `epid`
(різна місткість у підписі), а «Google Pixel» у видачі «iPhone 15» отримує свій
ключ і не змішується. Товари з ключем за назвою виводяться з міткою **«нижча
впевненість»** у `--discovery-report` і в самому Telegram-сповіщенні
(`price_history.json` → `key_conf`).

Лоти, з назви яких не вдалось витягти жодного значущого токена, не йдуть у
статистику (`N лот(ів) без ключа`).

### Історична медіана, а не live-видача

Кожен прогін дописує в `price_history.json` ціну (товар + доставка) кожного
нового спостереженого лота для його `product_key`.

- Поки для ключа менше ніж `MIN_HISTORY_POINTS` (**3**) точок за останні
  `HISTORY_WINDOW_DAYS` (**14**) днів — сповіщень **немає**, лише збір даних.
- Далі: `медіана` по вікну, і кожен **новий** лот порівнюється з нею.
  **Аномалія = ціна < `ANOMALY_THRESHOLD` × медіана** (за замовч. < 0.6, тобто
  дешевше за 60% типової ціни).

### Фільтр стану — через API, не через слова

У запит іде `filter=...,conditionIds:{1000|1500|1750|2000|2500}`
(New, New other, New with defects, Certified refurbished, Seller refurbished).
Свідомо **не** включені `3000/4000/5000/6000` (Used*) і `7000` (For parts) — для
нового/запечатаного стану «битий» не є поясненням низької ціни. Набір —
`SEARCH_CONDITION_IDS` (`config.py` / `.env`).

Лишився **тонкий запобіжник** `CONDITION_BLOCKLIST` — лише слова про
**пошкодження** (`defekt`, `Bastler`, `Teile fehlen`, `beschädigt`,
`for parts`, `not working`, `zum ausschlachten`). Слова `Ersatzteil` /
`Zubehör` / `Ersatz` навмисно **не** в списку: це не пошкодження, а звичайні
слова для сумісних фільтрів/щіток (на живих даних `ersatzteil` як стоп-слово
відсіювало ~590 валідних лотів за прогін).

### Фільтр репутації продавця

Лот ігнорується (без сповіщення), якщо `feedbackScore` <
`MIN_SELLER_FEEDBACK_SCORE` (**10**) або `feedbackPercentage` <
`MIN_SELLER_FEEDBACK_PCT` (**95.0**). Відсіює схему «акаунт-одноденка + −60%».
(У відстеження життєвого циклу такі лоти **потрапляють** — продаж від слабкого
продавця теж ринковий сигнал.)

## Вісь 2: ЛІКВІДНІСТЬ (наближений проксі)

Бот відстежує **життєвий цикл кожного лістингу** per-`product_key` у
`price_history.json` → `listings`: `first_seen`, `last_seen`, ціни, продавець,
`itemCreationDate`, `status`.

- Лістинг, якого немає у видачі `LISTING_GONE_AFTER_DAYS` (**2**) дні поспіль →
  `status = gone` (проксі «продано або знято»).
- З цього рахується за вікно `LIQUIDITY_WINDOW_DAYS` (**30** дн.):
  - **швидкість** — зникнень на тиждень;
  - **медіанний час до зникнення** — від `itemCreationDate` (або `first_seen`);
  - **активних пропозицій зараз** — поточна пропозиція.

### Рівні

| Рівень | Коли | Сенс |
|---|---|---|
| `UNKNOWN` | відстеження < `MIN_LIQUIDITY_TRACK_DAYS` (**14** дн.) або завершень циклу < `MIN_LIQUIDITY_EVENTS` (**3**) | даних замало — вирішувати вручну |
| `OK` | швидкість ≥ `LIQ_HIGH_PER_WEEK` (**1.5**) і час до продажу ≤ `LIQ_FAST_DAYS` (**12**) | швидко продається |
| `LOW` | швидкість < `LIQ_LOW_PER_WEEK` (**0.5**), або час > `LIQ_SLOW_DAYS` (**25**), або **затоварення** (≥ `SUPPLY_GLUT_MIN`=**5** активних і ~0 продажів) | гроші заморозяться |
| `MEDIUM` | усе інше | помірний попит |

**Ліквідність прогрівається довше за ціну:** ціновій медіані вистачає кількох
днів, а достовірному сигналу попиту — **2–4 тижні** полінгу. До того всі
сповіщення виходять з міткою `LIQUIDITY UNKNOWN` і ручна перевірка обов'язкова.

### Виявлення перевиставлення (relist)

eBay-продавці циклічно перевиставляють fixed-price лоти — `item_id` змінюється
**без жодного продажу**. Якщо після зникнення лота **той самий продавець** за
`RELIST_WINDOW_DAYS` (**5**) днів виставляє майже ідентичний (схожість назви ≥
`RELIST_TITLE_SIMILARITY`=**0.7**, ціна ±`RELIST_PRICE_TOLERANCE`=**6%**) —
попередній лот отримує `status = relisted` і **не рахується у швидкість
продажів**. Інакше velocity була б штучно завищена звичайним циклом
перевиставлення.

> Правило свідомо консервативне: прудкий продавець, який реально продав один лот
> і виставив інший, може бути порахований як relist. Це **занижує** швидкість, а
> не завищує — обраний бік помилки.

### Провайдер ліквідності (шов під реальні дані)

`config.MARKETPLACE_INSIGHTS_ENABLED` перемикає:

- `SelfTrackedLiquidity` — власний проксі (за замовчуванням);
- `MarketplaceInsightsLiquidity` — **заглушка**. Коли eBay надасть доступ до
  `buy/marketplace_insights/v1_beta/item_sales/search`, лишається реалізувати
  один метод `assess()` — інтерфейс `LiquidityReport` уже готовий, решта коду
  не змінюється.

**Подайте заявку на Marketplace Insights API вже зараз** (developer.ebay.com →
ваш keyset → App Check / API access requests) — погодження довге, гірше не буде.

## Режим розвідки (discovery mode)

Вузький список категорій, підібраний «з голови», — це евристика, а не дані. У
товарі, в якому не розбираєшся сам, легко переплатити за «рідкість», яку ніхто
не купує. Режим розвідки перевіряє ніші **на живих даних** перед тим, як
вмикати алерти.

### Робочий цикл

1. **Збір (~3 тижні).** `DISCOVERY_MODE=true` (за замовчуванням), широкий
   `CATEGORIES` (17 напрямків: витратні деталі, дитячі настолки/іграшки, запечатане колекційне, спорт-харчування). Запустіть
   `python main.py --interval` (= `POLL_INTERVAL_SECONDS`, 1800 c). Детектор,
   історія цін і ліквідність працюють як завжди, **але в Telegram нічого не
   йде** — кожен кандидат-аномалія (до фільтра ліквідності) дописується рядком
   у `discovery_log.jsonl`.
2. **Аналіз.** Через `DISCOVERY_PERIOD_DAYS` (21):
   ```bash
   python main.py --discovery-report
   ```
   Читає `discovery_log.jsonl` + `price_history.json`, друкує таблицю по
   категоріях і зберігає `discovery_report.md`. По кожній категорії:
   - скільки ключів товару відстежується (за `epid` / за назвою);
   - скільки кандидатів знайдено за період (**до** фільтра ліквідності), з них
     скільки нижчої впевненості (**LC** — ключ за назвою);
   - розподіл кандидатів по рівнях ліквідності (OK / MEDIUM / LOW / UNKNOWN);
   - медіанний % знижки серед кандидатів;
   - **`score = (кандидатів на тиждень) × (частка кандидатів з OK+MEDIUM
     ліквідністю)`** — категорії відсортовані за цим score, найкращі зверху.

   Категорія з багатьма кандидатами, але всі LOW/UNKNOWN → `score ≈ 0`: дешево
   трапляється часто, але перепродати нема кому. Саме це відсіює «хлам».
3. **Звуження.** Візьміть з хвоста звіту готовий блок `CATEGORIES = [...]`
   (категорії зі `score > 0` і часткою OK+MEDIUM ≥ 0.4), підставте `min_price`,
   вставте в `config.py`.
4. **Бойовий режим.** `DISCOVERY_MODE=false` у `.env`. Бот починає слати
   звичайні Telegram-сповіщення по звуженому списку. За потреби зменшіть
   `--interval` (напр. 900) — категорій тепер менше.

Приклад звіту — див. розділ [нижче](#приклад-розвідка-на-mock---simulate-days-21---discovery-report).

## Конфігураційні змінні (`config.py` / `.env`)

### Ціна

| Змінна | Замовч. | Призначення |
|---|---|---|
| `EBAY_MARKETPLACE_ID` | `EBAY_DE` | заголовок `X-EBAY-C-MARKETPLACE-ID` |
| `CURRENCY` / `PRICE_CURRENCY` | `EUR` | валюта форматування / валюта для `filter=price:[..]` |
| `CATEGORIES[i]["min_price"]` | per-category | нижній поріг ціни в `filter` обох запитів |
| `SEARCH_SORT_B` | `price` | sort для запиту B (запит A — без sort) |
| `ANOMALY_THRESHOLD` | `0.6` | аномалія, якщо ціна < поріг × історична медіана |
| `MIN_HISTORY_POINTS` | `3` | скільки спостережень треба для ключа перед аналізом |
| `HISTORY_WINDOW_DAYS` | `14` | вікно для цінової медіани |
| `SEARCH_CONDITION_IDS` | `1000\|1500\|1750\|2000\|2500` | дозволені `conditionId` у видачі |
| `MIN_PRICE` | `5.0` | глобальний фолбек, якщо у категорії немає `min_price` |
| `MIN_SELLER_FEEDBACK_SCORE` | `10` | мін. кількість відгуків продавця |
| `MIN_SELLER_FEEDBACK_PCT` | `95.0` | мін. % позитивних відгуків |

### Ліквідність

| Змінна | Замовч. | Призначення |
|---|---|---|
| `LIQUIDITY_WINDOW_DAYS` | `30` | вікно для метрик попиту |
| `MIN_LIQUIDITY_TRACK_DAYS` | `10` | доки менше — вердикт `UNKNOWN` |
| `MIN_LIQUIDITY_EVENTS` | `3` | завершень циклу для виходу з `UNKNOWN` |
| `LIQ_HIGH_PER_WEEK` | `1.5` | ≥ цього + швидкий продаж → `OK` |
| `LIQ_LOW_PER_WEEK` | `0.5` | < цього → `LOW` |
| `LIQ_FAST_DAYS` / `LIQ_SLOW_DAYS` | `12` / `25` | пороги медіанного часу до продажу |
| `SUPPLY_GLUT_MIN` | `5` | активних пропозицій для стану «затоварення» |
| `LISTING_GONE_AFTER_DAYS` | `2` | скільки днів відсутності = «зник» |
| `RELIST_WINDOW_DAYS` | `5` | вікно пошуку перевиставлення |
| `RELIST_PRICE_TOLERANCE` | `0.06` | допуск ціни для relist |
| `RELIST_TITLE_SIMILARITY` | `0.7` | поріг схожості назви для relist |
| `MARKETPLACE_INSIGHTS_ENABLED` | `off` | перемкнути на провайдера Insights API |

### Розвідка

| Змінна | Замовч. | Призначення |
|---|---|---|
| `DISCOVERY_MODE` | `true` | збирати дані без Telegram-сповіщень (кандидати → `discovery_log.jsonl`) |
| `DISCOVERY_PERIOD_DAYS` | `21` | орієнтовна тривалість розвідки (для звіту) |
| `DISCOVERY_LOG_FILE` | `discovery_log.jsonl` | лог кандидатів (JSON-рядки) |
| `DISCOVERY_REPORT_FILE` | `discovery_report.md` | куди `--discovery-report` пише таблицю |
| `POLL_INTERVAL_SECONDS` | `1800` | інтервал для `--interval` без значення (48 циклів/добу) |

### Інше

| Змінна | Замовч. | Призначення |

## 1. eBay App ID / Cert ID (Production)

1. <https://developer.ebay.com> → **Sign in** звичайним eBay-акаунтом. Окрема
   бізнес-реєстрація / Gewerbe **не потрібна**.
2. Меню з вашим ім'ям → **Application Keysets** → набір **Production**:
   - **App ID (Client ID)** → `.env` як `EBAY_APP_ID`
   - **Cert ID (Client Secret)** → `.env` як `EBAY_CERT_ID`
3. Browse API працює на **application access token** (OAuth2 Client Credentials
   Grant, `https://api.ebay.com/identity/v1/oauth2/token`, scope
   `https://api.ebay.com/oauth/api_scope`). Бот оновлює токен сам.
4. Keyset має бути **enabled**. Якщо пише «disabled — comply with marketplace
   deletion / apply for an exemption» — вкладка **Alerts & Notifications** →
   **Edit** → увімкнути **Exempted from Marketplace Account Deletion** (бот не
   зберігає персональних даних користувачів eBay). Поля endpoint / verification
   token лишити порожніми.
5. **Бюджет запитів.** Кожен цикл робить **2 виклики** `item_summary/search` на
   категорію (запити A + B), кожен з `limit=200` (максимум Browse API — ширша
   вибірка без додаткової вартості по кількості викликів). З N категоріями й
   інтервалом I секунд: `2 × N × (86400 / I)` запитів/добу.
   - зараз: **N = 17**, `I = 1800` c → `2 × 17 × 48` = **1632 запити/добу**
     ≈ **33%** від ліміту **5000/добу** — у межах з запасом.
   - якщо `2 × N × (86400 / I)` наближається до ~4500 — збільшуйте
     `POLL_INTERVAL_SECONDS` або скорочуйте `CATEGORIES`. `limit` на бюджет
     не впливає (це один виклик незалежно від розміру відповіді).
6. **Marketplace Insights API** (для реального сигналу продажів) — окрема заявка
   на тій самій сторінці keyset. Подавайте паралельно; коли дадуть — перемкніть
   `MARKETPLACE_INSIGHTS_ENABLED`.

```
    {"query": "Vorwerk Thermomix TM6 Zubehör", "min_price": <?>},   # score 0.47  ⚠ 2/3 за назвою
    ...
```

**Як читати:** категорії з високим score угорі; категорії з кандидатами, але
ліквідністю LOW/UNKNOWN падають у `score ≈ 0` — їх немає кому перепродати. Це і
є фільтр «хламу». Колонка **LC** / мітка **⚠** — скільки кандидатів згруповано
за назвою (нижча впевненість), бо `epid` не було. Мітка `—` у «~днів» — коли
`sold-проксі = 0`.

див. розділ [Формат сповіщення](#формат-сповіщення); три рівні заголовка
`PRICE OK · LIQUIDITY {OK|LOW|UNKNOWN}`, ніколи не глушиться, з посиланням на
sold-фільтр.

## Обробка помилок

- Тайм-аути та `ConnectionError` — експоненційний backoff
  (`BACKOFF_BASE`, `MAX_RETRIES`).
- `429 Too Many Requests` — пауза за `Retry-After` (або backoff).
- `5xx` від eBay — backoff і повтор.
- Помилка в одній категорії логується і **не зупиняє** решту та скрипт.
  У циклічному режимі невдалий прогін не рве цикл.
- Помилка провайдера ліквідності → сповіщення все одно йде з міткою `UNKNOWN`.
